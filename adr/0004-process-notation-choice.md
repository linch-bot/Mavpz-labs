# ADR-004: Вибір Activity-діаграми (Mermaid) для моделювання процесу оформлення й оплати

## Status

Accepted

## Context

Для Завдання 4 необхідно задокументувати бізнес-процес прецеденту `Checkout Order` (`Calculate Total` + `Process Payment`) з усіма сценаріями Лаб 2 в одній точній формі (Activity Diagram, BPMN 2.0 XML або машина станів) без дублювання у двох нотаціях.

## Decision Drivers

- Необхідність явно показати розподіл відповідальності між учасниками (`Customer`, `OrderService`, `PaymentGateway`), паралельне виконання (`fork`/`join`) і цикл повторної спроби оплати.
- Послідовність із `ADR-001` та попередніми роботами: текстова форма, що дифиться в Git і нативно рендериться в GitHub Markdown без зовнішніх інструментів.

## Considered Options

- **Опція 1: Activity-діаграма в Mermaid (`flowchart TD` зі swimlanes) (Обрано).**
  - _Плюси:_ Наочно показує зони відповідальності (swimlanes), послідовні й паралельні дії (`fork`/`join`), умови розгалуження, обмін повідомленнями та вузли даних (`Product`, `Order`); рендериться безпосередньо в GitHub.
  - _Мінуси:_ Вузли `fork`/`join` і сигнали в Mermaid емулюються графічними вузлами, а не окремими спеціалізованими примітивами синтаксису (на відміну від PlantUML).
- **Опція 2: Машина станів (`stateDiagram-v2`).**
  - _Плюси:_ Добре описує життєвий цикл однієї сутності (`Order`: `"Pending"` → `"Paid"`).
  - _Мінуси:_ Приховує виконавців дій (swimlanes), взаємодію з зовнішнім `PaymentGateway` та паралельне відправлення сповіщення клієнту й оновлення статусу.
- **Опція 3: BPMN 2.0 XML (`*.bpmn`).**
  - _Плюси:_ Стандартна типізація задач (`User Task`, `Service Task`) та пулів/лейнів із окремим `messageFlow`.
  - _Мінуси:_ Вимагає громіздкого XML-каркасу й експорту SVG/PNG із зовнішнього редактора (`bpmn.io` / Camunda Modeler) через відсутність нативного рендеру в GitHub.

## Decision

Обрано **Activity-діаграму у форматі Mermaid `flowchart TD`** зі swimlanes (`Customer`, `OrderService`, `PaymentGateway`) у файлі `process.md`.

## Consequences

Усі 3 Gherkin-сценарії Лаб 2 представлено як наскрізні шляхи на одній моделі з чітким розподілом відповідальності між ролями, без виділення БД у swimlane та зі збереженням єдиного стеку Mermaid у репозиторії.
